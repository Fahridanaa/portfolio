I learn a framework best by shipping something real. Komikrr was that project: a comic reader with its own data pipeline, not another tutorial.

### The problem

I wanted to take SvelteKit past the tutorial stage. A reader gave me the pieces a real app needs: server routes, a database, long lists, and a lot of images. The source site is rate-limited, so the ingestion could not be a tight loop.

### What I built

Komikrr is a SvelteKit 2 app on Svelte 5. The home page has a featured carousel, a popular row, and a latest-updates grid. Genre pages group the library, the comic page carries the metadata and chapter list, and the reader renders a chapter as one vertical strip with previous and next links.

![Komikrr home page and chapter reader](public/assets/projects/komikrr/demo.gif)

The data comes from a second repo, `comic_scraper_api`. It takes a Komikcast title, parses the metadata and chapter list with BeautifulSoup, and downloads the chapter images with `aiohttp`. Three downloads run at a time, with retries and backoff, a random user agent, and a two-to-five second delay between requests. Covers go to Cloudinary under `{slug}`; pages go under `{slug}/chapter-{n}`. Metadata goes to PostgreSQL through SQLAlchemy. Folders that already exist are skipped, so a rerun continues where the last one stopped.

The SvelteKit side reads the comic rows from PostgreSQL with Drizzle and asks Cloudinary for the chapter folders and page images. The reader never touches Komikcast.

### The result

The result is a reader that works end to end. One scraper run fills PostgreSQL and Cloudinary, and the app serves the library from there. A new series is a rerun, not a code change.
